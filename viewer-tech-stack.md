# Tech Stack Recommendation: 3D Model Viewer App

**Status:** Draft
**Scope:** cross-platform mobile viewer for CAD/architecture files (SketchUp-style) with cloud sync, measurement/annotation, live presentation, and AR placement.

---

## 1. Architecture Overview

The stack is organized by **where each piece runs**, not by vendor:

```
┌─────────────────────────────────────────────┐
│  Client apps                                 │
│  Native iOS & Android                        │
└───────────────────┬───────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│  3D & AR engine                              │
│  Filament, ARKit, ARCore                     │
└───────────────────┬───────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│  Sync & storage                              │
│  Trimble Connect, cloud object storage       │
└───────────────────┬───────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│  Backend services                            │
│  APIs, auth, database                        │
└─────────────────────────────────────────────┘
```

Color logic (conceptual, for any diagram built from this doc): **on-device** (client apps + 3D/AR engine) / **transport & sync** (bridge layer) / **server-side** (backend) — three distinct zones of responsibility, not a rainbow of unrelated technologies.

---

## 2. Layer 1 — Client Apps

**Recommendation:** native, not cross-platform.

| Platform | Stack |
|---|---|
| iOS | Swift + SwiftUI (UIKit for fine-grained gesture handling where needed) |
| Android | Kotlin + Jetpack Compose |

**Why not React Native / Flutter:** in this app, rendering speed and AR tracking quality *are* the product. Cross-platform frameworks add a JS/Dart bridge on top of exactly the two things that most need to be fast — frame rendering and gesture-driven model manipulation. The cost of native (two codebases) is worth paying here, the same tradeoff SketchUp Viewer itself makes.

---

## 3. Layer 2 — 3D & AR Engine

| Concern | Choice | Notes |
|---|---|---|
| Rendering | [Filament](https://google.github.io/filament/) (Google's open-source PBR renderer), shared C++ core wrapped per-platform | The one place code *is* shared — rendering math doesn't care what platform it runs on |
| AR (iOS) | ARKit | Best-in-class plane detection & lighting estimation on iOS |
| AR (Android) | ARCore | Android equivalent |
| CAD parsing | [SketchUp SDK](https://extensions.sketchup.com/) (or a licensed `.skp` parser) | Reads geometry, materials, scenes, and camera data directly out of the file format — no reliable substitute exists |

**Alternative worth naming:** Unity + AR Foundation would let you share rendering *and* AR logic in one codebase. Faster to ship, but you inherit Unity's runtime size, licensing terms, and a less native feel for a precision/measurement tool. Reasonable choice for a small team prioritizing speed-to-ship over rendering ceiling and native polish.

---

## 4. Layer 3 — Sync & Storage

| Concern | Choice | Notes |
|---|---|---|
| File source | Trimble Connect API | Matches the existing ecosystem this kind of app plugs into |
| OS file integration | Files app (iOS) / Storage Access Framework (Android) | Native "open from Files" flow |
| Object storage | S3-compatible storage | For AR captures, exports, thumbnails generated by the app |
| Local/offline cache | SQLite — GRDB (iOS) / Room (Android) | Field use means unreliable site Wi-Fi; recently opened models must work offline |

---

## 5. Layer 4 — Backend Services

Deliberately boring — this layer's job is auth, metadata, and presence, not rendering.

| Concern | Choice | Why |
|---|---|---|
| API layer | Go (or Node/TypeScript), REST or GraphQL | Fast, small footprint, scales horizontally |
| Database | PostgreSQL | Relational project/user metadata, battle-tested |
| Cache / presence | Redis | Session state, "who's viewing this scene right now" |
| Real-time collaboration | WebSocket service (self-hosted or managed — Ably/Pusher) | Syncs camera position/scene state during live presentations |
| Auth | OAuth2 / OpenID Connect (tying into an existing identity provider, e.g. Trimble ID, if integrating with that ecosystem) | Don't build your own auth |

---

## 6. Supporting Tooling

| Concern | Choice | Notes |
|---|---|---|
| CI/CD | Fastlane + GitHub Actions (or Bitrise) | Build/sign/upload automation for both platforms |
| Crash & performance monitoring | Firebase Crashlytics or Sentry | Pair with in-app frame-rate telemetry — AR/3D apps fail in GPU/thermal ways generic analytics miss |
| Testing (app logic) | XCTest (iOS), Espresso (Android) | Standard native test frameworks |
| Testing (renderer) | Golden-image regression tests | Render a known scene, diff against a reference image, rather than unit-testing 3D math directly |

---

## 7. Bottom-Line Recommendation

- **Native** Swift/Kotlin apps — not cross-platform.
- **Shared Filament rendering core**, native ARKit/ARCore for AR tracking.
- **Trimble Connect** for file sync, S3 for generated assets, SQLite for offline cache.
- **Go + PostgreSQL + Redis** backend, WebSocket for live presentation sync.
- The one real fork in the road: **native vs. Unity** for the render/AR layer. Recommendation is native, since this is a precision tool (measurement, true-scale AR) rather than a game — rendering fidelity and platform-native feel matter more than shipping speed here.

## 8. Open Questions

- Is there an existing identity provider (Trimble ID or similar) to integrate auth against, or does this need to stand alone?
- What's the expected offline duration on a job site — does the local cache need full read/write (edits queued for sync) or just read-only viewing?
- Is live multi-user presentation (multiple viewers watching one presenter's camera move in real time) a v1 requirement, or a later addition? This determines how early the WebSocket/presence layer needs to be built.
